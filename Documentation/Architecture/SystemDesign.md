# System architecture — Stage 1 design

**Status:** design only. See the [master specification](../MasterSpecification.md) for requirements and the [project record](../Decisions/ProjectRecord.md) for decisions, status and approvals. A [web preview](../../Frontend/README.md) uses prewritten fixtures and [read-only web status and sample-delivery APIs](../../Backend/README.md). The separate [Access Lab](../../Backend/AuthLab.md) tests password hashing, TOTP and sessions using synthetic, temporary identities only. A [separate local SQLite exercise](../Testing/SQLiteStorageChecks.md) saves only synthetic snapshots and has no web endpoint; the [Sample History preview](../Testing/SampleHistoryChecks.md) serves an independently verified copy read-only. No production user store, EA, broker data, operational database or command protocol is implemented.

## Ownership of decisions

| Component | Owns | Does not own |
|---|---|---|
| Windows MT5 + native MQL5 EA | Eight instrument feeds, local signals and shadow trades, all broker actions, whole-account entry protection, per-position management and recovery. | Browser authentication or remote reporting. |
| Python / FastAPI local service | Authenticated dashboard API, validated control requests, message bridge, SQLite and analytics, Telegram delivery and audit. | Trading credentials, decision deadlines or broker orders. |
| React / Vite dashboard | Monitoring, configuration requests, explicit authorisation, alerts and analytics. | Direct orders or a guarantee of protection while unreachable. |
| Broker | Actual orders, deals and confirmed server-side SL/TP where supported. | EA trailing/logic, same-price fills or reconstruction of a missed equity peak. |

The broker adapter holds feed mapping, contract and execution constraints, margin and calendar integration. Strategies depend on shared features and capabilities, not on the string `Exness`. Windows is the first deployment; remote access and PostgreSQL are later options, not Stage 1 dependencies.

## Market, signal and order path

1. **Ingest:** One execution owner per account. Select and map the eight configured symbols. `OnTick` only fires for the attached chart and events can coalesce; use bounded, per-symbol reads from the terminal tick buffer and timestamp-aware cursors, including ties. Track observed gaps and stale quotes; do not assert capture of every upstream tick. Warm up without blocking order management, then build in-memory 1/5/10-second aggregates with empty intervals marked. Compute M5 structure, M3 setup, M1 refinement and optional H1 context without leaking future bar data. See [OnTick](https://www.mql5.com/en/docs/event_handlers/ontick) and [CopyTicks](https://www.mql5.com/en/docs/series/copyticks).
2. **Evaluate:** Independently test tick, momentum, volatility, statistical, structure, execution, strategy-performance and regime engines. A candidate carries its strategy, intended side, invalidation price, estimated available move, expected cost and decision version. Hard gates veto any rank or score. Start with transparent rules and statistically testable baselines. Adapt only within offline-validated bounds, with logged changes, sufficient sample size, shadow validation and rollback. No online AI API. Broker-facing ML is optional and held until terms and results justify it.
3. **Check and execute:** Require retail hedging mode and opposite-position permission. Check all eight mappings, freshness, selected instrument, daily state, measured execution conditions, account-wide risk and projected margin. Use executable bid/ask and account-currency calculations, with commission, funding where relevant, and slippage buffers; do not double-count spread if using executable prices. Round volume down to the broker grid. Reject below-minimum volume; never shrink a valid structural stop to force an entry. Check volume steps, partial-fill and residual volume, tick size, stop/freeze levels, session, expiry and filling modes. Select market/limit/stop based on measured behaviour and broker capability. Reconcile order, deal and position as distinct records. Acknowledged submission is not a fill. Record request IDs, stage, outcome and all rejection codes; never blindly retry an ambiguous submission.
4. **Protect and exit:** Prefer a broker-side stop in the initial request and verify the actual position has valid protection. No unverified unprotected entry path. Strategy-specific exits and partial closes consider invalidation, momentum, costs, net profit and remaining opportunity. For every ticket, improve or preserve its protective stop, never widen it. Account for both sides of the trade and costs when computing effective break-even, without promising a zero-loss fill. Manual positions on the eight instruments enter management and risk calculations and have distinct attribution. For a manual trade without a stop, attempt protection when possible, alert and follow the approved emergency policy if it cannot be protected. Other exposure still counts for account-level risk; management permission does not extend to unrelated trades by implication.

## Live modes and control requests

- Disabled new entries, shadow, armed, managing-only, emergency and recovery are distinct conditions. **Dashboard Off** means no new entries; it does not turn off EA position management. MT5's own Algo Trading switch also disables EA-driven protective modifications and closes. Once an approved EA manages positions, the dashboard's Off/emergency controls and native EA fallback must not be confused with that terminal switch. During Stage 1, leave Algo Trading off because there is no EA to manage anything.
- One instrument can generate new EA entries; scopes for managing positions and assessing exposure are broader. On a switch, disarm old entries, request cancellation of old EA-owned entry orders, and reconcile pending/in-flight broker orders before arming the new instrument. Show **switch pending** until confirmed. A pending server order can race cancellation or trigger during an outage. Use protective stops and broker-held expiry if proven, reserve risk for pending/in-flight entries, and handle race fills as existing positions; never represent an unconfirmed switch as applied. For symbols without safe expiry/cancel behaviour, the affected pending route is not eligible.
- Stops/slippage: broker-confirmed protections can work after disconnection, but gaps, market closures, broker constraints or outages may delay actions or cause fills beyond modeled losses. A stop is not a guarantee of execution at the stop price. The requested maximum slippage is an entry/reliability gate and post-fill breach threshold where the venue cannot enforce a bound. If a strategy requires a guaranteed entry price bound, it cannot use an order route that has no enforceable bound. Slippage does not justify ignoring protective exits.
- Do not silently carry authorisation across EA/terminal restart. Reconcile from broker state plus durable account-scoped checkpoints; recover known stops, trailing ownership, pending orders, deals, equity and loss latches. Require fresh manual authorisation for new entries. Provide native monitoring/entry-pause access even without the dashboard. If MT5 or the broker link is down, the EA cannot send amendments, cancellations or closes. UI shows last heartbeat, snapshot age and command acknowledgement; it must not report “stopped/flat” merely because an operator clicked a button.

## Selected risk requirements (not revised)

| Rule | Requirement |
|---|---|
| Per new position | At most **10%** of current equity in calculated loss at stress-adjusted stop. Dynamic sizing may use less. |
| Aggregate exposure | At most **40%** of equity in modeled aggregate open risk before adding exposure. Include manual positions, correlated exposure, pending/in-flight risks and any newly unhedged side. Do not offset stops as if a hedge cannot unwind. |
| Margin | Projected used margin at most **70%** of equity, also checking free margin, stop-out and margin shocks. `OrderCalcMargin` is standalone; combine current exposure, broker preflight where available and stressed scenarios. |
| Daily drawdown | Latch at or beyond **40%** down from the highest observed equity for the broker day, including floating P/L. With a $150 peak, act at $90 or below. No early reset. |
| Daily target | **+1,500%** of starting daily equity: threshold is **16×** starting equity, with equity reflecting realized and floating results and booked costs. Latch entries off at target even if equity later falls; continue management, then monitor when flat. Resume only after next verified daily reset or explicitly authorised config change, and never override a higher-priority protection. |
| Position limit and compounding | Default position limit around **five**; increases are conditional on justified equity, risk, margin and execution. Recalculate size from updated equity, not from last trade win. |
| Lifetime drawdown | Track and display; **no separate lifetime shutdown**. |

Observe and persist day key, start equity, high-water equity, latches and coverage quality using broker time. Exness's **00:00 server** reset is an application boundary, separate from commercial rollover and swap. Poll for new broker data; do not infer a new broker day from the Windows clock alone. When a mid-day first install, data loss or disconnected rollover prevents verifying start/peak, retain known state, mark the missing window and block new entries until a trustworthy boundary/baseline is established. Do not fabricate missing equity. London and New York session DST rules are separate from server time; use versioned time-zone mappings. Agreement on external cash flows and the exact emergency action is deferred to before order-capable testing. Deposits must not be reported as strategy profit.

## Local communication and security

**Proposed for prototype:** use a bounded, versioned local mailbox under the dedicated terminal's `MQL5/Files` sandbox, consumed asynchronously by Python. The local dashboard communicates with FastAPI; the backend translates permitted requests into mailbox messages. This avoids putting MT5's synchronous [`WebRequest`](https://www.mql5.com/en/docs/network/webrequest) inside the execution loop. Even a timer callback in the same EA can stall its handling of other events. Stage 2/7 must measure file stall risk and validate file atomicity on Windows before choosing the final transport. Use per-environment/account namespaces, independent bounded queues and file size limits, temporary-to-ready file handoff, separate command and telemetry channels, restricted Windows file permissions and a separate provisioned command authentication key. Keep the last known safe local configuration when the API is down; continue existing protection without acknowledgements.

- Start with API bound to **loopback** (this PC only). Responsive design does not imply phone network access. For later phone/remote control, explicitly approve an authenticated private tunnel/VPN and TLS; do not expose the raw API port to the Internet. No browser-origin or unauthenticated bypass.
- Plan Argon2id password hashing, authenticator-app two-factor (TOTP), securely protected TOTP secrets and one-time recovery codes, rate limiting, login history, expiring server-side sessions, secure cookies on TLS, and request-origin/CSRF protection. Require appropriate permissions and confirmation/re-authentication to arm or change sensitive config. Emergency protection is accessible to an already authenticated operator without a fresh login; it is logged and still requires EA acknowledgement. Verify Windows and application permissions separately.
- EA validates schema/version, account/environment scope, command authentication, expiry, sequence/idempotency and hard limits. Use receipt and applied/rejected status; a replay or out-of-order command cannot re-enable trading. Restart creates a new arming context. Treat a compromised Windows account as outside the protective boundary of a file mailbox. No credentials in `.mq5` inputs, repository, source, screenshots or logs. Prefer an audited standard message-authentication implementation and test vectors, not ad hoc encryption.
- Dashboard, Telegram and MT5 push are independent, configurable alert sinks; they can be unavailable and must not block protection. Tag alerts as broker demo, broker real or shadow, and show staleness. MT5 and Telegram outbound credentials/config are provisioned separately. Default to no externally sent account-identifying details.

## Data and auditing

Use SQLite migrations and transactional writes behind a persistence layer. The v0.5 local exercise verifies a first versioned schema, transactional sample writes, reopen and backup restoration. It is not the production telemetry schema or a decision on the PostgreSQL migration path. Record timestamps with source/time-zone evidence, quote/bid/ask context, events and reason codes, costs, account/environment labels, data health, applied config version, and strategy/model version. Distinguish **actual real**, **actual demo**, **shadow**, and **estimated** values, including estimated missed opportunities and losses avoided; ratios with small samples should be suppressed or labelled insufficient.

- Buffer ticks in bounded batches. Checkpoint critical protection state independently of the database and write decisions with deduplicating IDs. Treat every *evaluated candidate* (not every quote) as an auditable row. Rebuild dashboard state from reconciled broker events after an outage.
- Keep one year of detailed ticks with observed-coverage metadata; accumulate and backfill only when broker data are available. Benchmark bulk-ingest storage, using partitioned tick chunks and SQLite metadata if measured throughput calls for it. Archive older chunks with compression, checksums and a tested restore. Keep decision/trade/strategy/account records indefinitely subject to capacity and backups. Report disk pressure, data loss or retention gaps; never silently pretend history exists. If safety/audit data cannot be persisted, keep protection running and disallow new entries until safe.
- Use tested encrypted backups, including a transactionally consistent database snapshot. A private repo is for source and clean fixtures, not broker quotes, account records, logs, backups or secrets.
